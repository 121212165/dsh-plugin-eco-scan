# 领域扫描 D2：医疗健康领域

> 分析员：D2（医疗健康领域）｜数据快照：2026-11-16｜数据源：`data/eco-data.json`（38,549 仓）、`data/digest.md`、`data/AGENT_BRIEF.md`、`data/reports/RETRO.md`
>
> **口径与方法（先说清楚，否则数字不可信）**
> - `rows[].tags` 存的是**数字下标**（即 `meta.tags[id]` 的索引），而 `meta.tags[].id` 是英文 slug（如 `health`/`security`）。本报告统一用**下标映射**解析标签（见 Part B-2，这是一个新发现的工具坑）。
> - 医疗健康是**垂直行业**，而 50 个能力标签全是**功能维度**（RAG/安全/数据库…），数据里没有"行业/vertical"字段。因此只能用仓库名关键词做启发式分类，再做人工逐条复核。
> - 单快照、`velocity.overlap=0`，增长率仅作方向性参考；周下载仅覆盖 7,001/38,549 仓（18.2%），在医疗这种小众垂直域覆盖率更低（见 Part B-6），需求可能被系统性低估。
> - "高分仓"统一指 `score ≥ 75`；"真医疗"= 关键词命中后经人工复核确认与医疗/健康相关的仓库。所有数字均来自 `data/.scratch/d2_*.cjs` 对原始 `eco-data.json` 的单次贯通统计，可复算。

### A1. 数据漏斗：422 个关键词命中里，只有 116 个是真医疗

我用 88 个中英文医疗/健康关键词（`med*/clinic/patient/mri/icd/vaccine/sleep/health/…`）对 38,549 个仓库名做全量匹配，再人工分流，得到一条非常刺眼的漏斗：

2. **"doctor / triage / health" 是调试工具的隐喻，不是医疗。** 工具隐喻仓 **112 个**，是真临床 **40 个的 2.8 倍**，周下载合计 13,314 反而**高于真临床的 3,520**。典型如 `perrylink/dsh-plugin-doctor`、`xinstart-1/dsh-log-triage`、`omdsh-dev/dsh-session-health`、`hardlic/dsh-plugin-health-check` —— 全是"会话体检/日志分诊"，与医疗无关。**任何按 `doctor/health/triage` 关键词做的医疗供给统计都会高估 2–3 倍。**
3. **头部极度集中、长尾全是低质克隆。** 健康域 116 仓里只有 13 个有周下载（**11.2%**）；`easonmws/dsh-plugin-health`（wk **5,537**）单仓就占健康域周下载总量的 **49%**，但它标签是 `[命令行, Git/提交, 插件市场, 安装/管理]`，**没有打任何健康/医疗标签**——生态分类里"健康"是隐形的。

## Part B — 新问题发现（RETRO.md 7 条之外）

> 以下均为本轮 D2 执行中**实际踩到/观测到**的问题。与 RETRO 7 条逐条比对后确认不重复（尤其区别于 #1 数据入口、#2 行字段映射、#5 onboarding、#6 runbook、#7 单快照）。每条给出可直接提 issue 的标题。

### B-1. 任务 prompt 里的 `RETRO.md` 路径是错的（多一次失败读取 + 漏读风险）
- **现象**：任务书写"读取 AGENT_BRIEF.md、digest.md、eco-data.json（路径在 `...\data\`），以及 RETRO.md"——前三个文件确实在 `data/`，但 `RETRO.md` 实际位于 `data/reports/RETRO.md`。我按提示路径读取直接返回 `File not found`，只能再 glob 搜索才找到。
- **影响**：每个子代理都要浪费一次工具调用；更严重的是，若代理不主动恢复、直接跳过 RETRO，就会**重复 RETRO 已记录的 7 个坑**（本任务明确要求避开）——质量直接下降。
- **证据**：`read("C:\...\data\RETRO.md")` → `{"error":{"type":"tool.execution","message":"File not found"}}`；随后 `glob("**/RETRO.md")` 定位到 `data/reports/RETRO.md`。
- **建议**：提 issue「修正领域扫描任务模板中的 RETRO.md 绝对路径」。把所有输入文件的**完整绝对路径**写进任务模板（或在 `data/RETRO.md` 放一个指向 `reports/RETRO.md` 的副本/软链），并在 prompt 末尾加一句"若读取失败必须 glob 查找不得跳过"。

### B-2. `meta.tags[].id` 是英文 slug，`rows[].tags` 用数字下标——无映射表导致标签解析全空
- **现象**：`rows[].tags` 存数字（如 `[18,19,21,25]`），而 `meta.tags[]` 的 `id` 是字符串 slug（`video`/`health`/`security`）。我最初按直觉写 `tags.find(t => t.id === rowTagId)`，**每一个标签都返回 undefined**，输出的标签列表全是 `[]`、`[/]`、`[///]`。正确做法是 `meta.tags[rowTagId]`（数字下标即 id）。注意 `AGENT_BRIEF.md` 用的是数字 id（0视频…46诊断/自检），而 JSON 里是 slug，**两套口径没有一处明示对应关系**。
- **影响**：本生态所有报告的核心结论都建立在标签统计上（RAG/安全/成本空白等）。代理一旦用错映射，会得出"所有仓库都没有标签"的结论而毫无报错——**静默错误比崩溃更危险**。这与 RETRO #2（行字段 row[10]/row[11] 错位）是**不同的两个坑**：一个是行的位置字段，一个是标签表的 id 表示。
- **证据**：`d.meta.tags[0] = {"id":"video","name":"视频/分镜"}`、`d.meta.tags[39] = {"id":"security","name":"安全"}`、`d.meta.tags[46] = {"id":"health","name":"诊断/自检"}`；而 `d.rows[0][9] = [18,19,21,25]`。按 slug 查找命中 0 个，按下标查找全部命中。
- **建议**：提 issue「为 meta.tags 增加数字 id 映射并写入 DATA-DICTIONARY」。在 `meta` 增加 `tagById: {"0":{...},...}` 或把 `meta.tags[].id` 改为数字、slug 移到 `slug` 字段；`digest.mjs` 输出一张唯一的"数字 id ↔ slug ↔ 名称"对照表作为 agent 唯一口径；把这条陷阱补进 `AGENT_BRIEF.md` 的字段字典章节。

### B-3. 没有垂直行业维度，且 doctor/triage/health 是调试术语——领域统计必然高估 2–3 倍
- **现象**：50 个能力标签全是功能维度（RAG/安全/数据库…），`meta.segments` 也只是 framework-runtime/ui-client 等功能赛道，**没有任何"医疗/金融/教育"行业字段**。做领域扫描只能靠仓库名关键词。而 `doctor`/`health`/`triage` 在插件语境里绝大多数是"插件体检/日志分诊/会话健康"的隐喻：工具隐喻 **112 仓**，真临床 **40 仓**，比值 **2.8:1**；工具隐喻周下载 13,314 反而高于真临床 3,520。
- **影响**：医疗领域的"供给数量""热度"若直接用关键词统计会被放大近 3 倍，导致错误地判定该领域"已经很拥挤"而放弃开发（本报告的 A1 漏斗就是为了纠正这一点才做的）。其它垂直领域（金融/法律/教育）扫描会踩同样的坑。
- **证据**：`d2_funnel.cjs` 单次贯通统计：关键词原始命中 422 → 严格临床 40 / 健康生活 76 / 工具隐喻 112 / 其它误命中 194；`uckkk/dsh-doctor` 类、`perrylink/dsh-plugin-doctor`、`xinstart-1/dsh-log-triage`、`omdsh-dev/dsh-session-health` 均非医疗。
- **建议**：提 issue「增加垂直行业分类字段或提供权威关键词白名单」。短期：在 `AGENT_BRIEF.md` 为每个常见垂直域提供"包含词/排除词"清单（如医疗排除 doctor/triage/system-health 隐喻）；中期：数据侧新增 `vertical` 字段（med/finance/edu/…）或从 description 做二次标注，让领域统计有可信口径。

### B-4. 单一账号 1,296 仓的"插件农场"污染所有计数与"新仓"指标
- **现象**：`uckkk` 账号发布 **1,296 仓**（占全库 3.4%），分数全部挤在 **47.1–51.3**，年龄 65–92 天，仅 **3 仓有周下载**；其中 22 个是医疗健康仓，全部 score 48.8、零下载（`dsh-vaccine`/`dsh-dental-check`/`dsh-sleep-cycle`…）。全库 ≥100 仓的账号有 5 个、合计 **1,905 仓（4.9%）**；≥50 仓的 13 个账号合计 **2,487 仓（6.5%）**。
- **影响**：这些农场仓直接灌水了标签计数、关键词命中数、`new30=14,695` 新仓指标和各领域"供给量"。本报告中"22 个医疗健康农场仓"若被当成真供给，会把医疗域供给凭空抬高 ~19%（22/116）。**所有基于"仓库数量"的供需判断都被农场系统性扭曲**，且与 RETRO #7（增长率不可信）是两个独立问题。
- **证据**：`d2_final.cjs`：uckkk 1,296 仓、score 47.1–51.3、age 65–92d、3 仓有周下载；`d2_tags.cjs`：uckkk 占健康域 22 仓；top-owner 统计：前 5 账号 1,905 仓。
- **建议**：提 issue「在 digest 中提供农场/低质克隆过滤视图」。给 `rows[]` 增加 `isFarm` 标记（单一 owner 仓库数 ≥ 阈值且分数集中在窄区间且周下载为空），`digest.md` 同时输出"全量口径"和"去农场口径"两套标签计数；分析类报告强制声明使用哪套口径，避免把灌水当需求。

### B-5. AGENT_BRIEF 未覆盖"领域扫描"任务类型及其输出路径契约
- **现象**：`data/AGENT_BRIEF.md`（44 行）通篇描述的是原任务（A1–A10 当前需求、E1–E5 企业需求→报告一/二→总结），**完全没有提到领域扫描 D1–Dn，也没有 `data/reports/domains/` 目录或 `D2.md` 的输出约定**。本次 D2 的输出路径只存在于父会话的 prompt 里；我读 brief 时无法确认输出契约，而兄弟代理 D4/D5 正在往同一个 `reports/domains/` 目录写文件，彼此之间没有清单或合并校验。
- **影响**：子代理一旦丢失/误解 prompt 上下文，就没有唯一权威来源确认"我该输出什么、写到哪里"；并行代理写共享目录缺少命名/清单约定，父代理只能靠 glob 碰运气收齐，漏收或覆盖的风险高。这不同于 RETRO #5（当时连 brief 都没有）——现在 brief 有了但对新任务类型已过时。
- **证据**：完整读取 `AGENT_BRIEF.md` 44 行，0 处出现 `domains`/`D2`/`领域扫描`；首次读 `reports/` 目录时无 `domains/`，随后出现 `D4.md`/`D5.md`（兄弟代理并发写入）。
- **建议**：提 issue「更新 AGENT_BRIEF 增加领域扫描章节与产物清单」。在 brief 增加"领域扫描任务"小节，列出 D1–Dn 的主题与固定输出路径 `data/reports/domains/Dn.md`；建立 `data/reports/domains/MANIFEST.md` 登记各域文件与状态，父代理按清单校验齐全性后再合并（呼应 RETRO #6 的质量门禁思路，但针对的是新增的领域扫描波次）。

### B-6. 垂直域周下载覆盖率仅 11.2%，领域需求信号在数据层几乎不可见
- **现象**：全库周下载覆盖率为 18.16%（`reachCoveragePct`，主榜 37.02%），但真医疗健康域 116 仓中只有 13 个有周下载（**11.2%**）；严格临床 40 仓中只有 5 个有周下载（**12.5%**），周下载合计仅 3,520（全库 7,837,245 的 0.045%）。
- **影响**：报告里所有"医疗需求弱"的判断都可能是**数据覆盖偏差**而非真实需求——小众垂直域的仓库更可能是新建、未被 npm 索引的低信号仓，正好落在那 19,868 个 `lowSignal` 里。这会引导决策者错误地放弃一个其实存在但未被数据捕捉的市场（与 RETRO #7 的单快照局限相关，但这里是**垂直域覆盖不足**这一具体表现）。
- **证据**：`d2_funnel.cjs`：健康域 116 仓仅 13 有周下载；`d2_final.cjs`：严格临床 40 仓仅 5 有周下载、周下载合计 3,520；`digest.md`：`weeklyPositive=7,001/38,549`、`lowSignal=19,868`。
- **建议**：提 issue「对垂直领域仓做定向富化以提升周下载覆盖」。扫描器对医疗等垂直域的仓库优先调用 npm/下载量富化（enrichment，目前 `enriched=174` 太少），并在 `digest.md` 分域输出 `reachCoveragePct`；分析报告中把"领域周下载覆盖率"作为必填的可信度指标，覆盖率 <15% 时禁止下"需求弱"的结论。
