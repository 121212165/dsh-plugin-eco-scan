# 企业未满足需求分析 — E4：企业集成、网关与平台治理

> 研究员：E4 ｜ 分工主题：**企业集成、网关与平台治理未满足需求**
> 数据基线：`eco-data.json`（快照 2026-11-16，38,549 仓、50 能力标签）+ `digest.md` 权威摘要 + `REPORT-1-synthesis.md`（任务一结论）。
> 企业视角的核心诉求：**统一纳管、可控接入、可审计**（unified control / governed access / auditable）。
> 口径说明：本文「矩阵格」数字取自 `meta.matrix` 权威矩阵（如工作区×路由=28），「标签交集」数字为全量 rows 按 tag 数组二次统计（含低信号仓，故大于矩阵格），两者不可直接相减但方向一致。增长率为单快照样本信号（`velocity.overlap=0`），周下载仅覆盖 7,001/38,549 仓。

## 0. 执行摘要：企业要"治理层"，生态给的是"单点工具"

把 50 个标签按企业漏斗重排后，出现一个非常清晰的结构性错配：

| 企业需要的治理能力 | 生态现状（具体数字） | 判断 |
|---|---|---|
| 统一入口/底座 | 框架/运行时族 1,795 仓、周下载 1,337,335，其中 `deepseek-ai/deepseek-harness` 单仓 1,208,788 = **90.4%**；第三方最高 `drscrewdriver/dsh-thinking-levels` 仅 4,105 | 底座被官方单仓垄断，**第三方治理层真空** |
| 路由/网关 | 路由/网关标签仅 **1,191 仓**，主榜 **0 仓**，`score≥90` 仅 **9**（0.76%）；`alice-marx/dsh-model-router` 增长 **-70.1%** | 需求迫切但供给薄、生命周期短 |
| 权限门控 | 名称含 `rbac` 的仓库 **0**；`permission` 27 仓中仅 3 仓有下载；`MCP×安全` 仅 94 仓且 `score≥90`=1 | "可控接入"几乎无人做 |
| 可审计 | 名称含 `audit` 104 仓但仅 15 仓有下载；`compliance` 仅 8 仓；`安装/管理×安全` 164 仓增长中位 **-5.8%** | 审计/合规是最薄的一层 |
| 注册中心 | `MCP` 1,962 仓，但 `MCP×工作流` 仅 **58**（2.96%）、`MCP×路由` 仅 43；唯一像注册中心的 `drscrewdriver/dsh-mcp-registry` 仅 wk 2,521 | "注册—发现—编排"链路断裂 |

**一句话结论**：生态已经把"功能插件"做得极多（安装/管理 3,001 仓、MCP 1,962 仓、IM 1,410 仓），但企业真正买单的"把多方能力收敛为可控、可审计的一条治理链路"几乎没有成品。任务一 Top15 中有 6 项（WorkspaceGuard、多 Provider 预算管家、WorkspaceRouter、插件健康自检、远程控制、技能审批）本质都是治理层——本报告从企业视角把这 6 项进一步收敛为 **6 大未满足需求**，并给出硬证据。

## 1. MCP 注册中心/网关与权限门控

### 1.1 供给总量大、治理交集极小

- `MCP` 标签 **1,962 仓**（主榜 54，周下载合计 360,148，`score≥90` 23）；名称含 `mcp` 的 475 仓中 `score≥90` 仅 5——高分 MCP 工具集中在少数仓库。
- 但把 MCP 与企业治理能力交叉后，供给塌缩：

| 交集 | 仓库数 | 主榜 | `score≥90` | 说明 |
|---|---|---|---|---|
| MCP × 工作流(29) | **58** | 0 | 1 | 仅占 MCP 总量 2.96%，"注册后能编排"几乎空白 |
| MCP × 路由/网关(32) | 43 | 0 | 0 | 无一个高分"MCP 网关" |
| MCP × 安全(39) | 94 | 2 | 1 | 权限门控/审计接近真空 |
| MCP × 安装/管理(41) | 154 | 0 | 1 | 安装多、治理少 |
| 矩阵：工作区×MCP | 73（new30=27） | — | — | 新仓在补，但存量仍薄 |
| 矩阵：技能/Prompt×MCP | 170（new30=51） | — | — | 相对活跃，但缺权限维度 |

- 企业治理关键词命中极稀疏：`rbac` **0** 仓、`permission` 27 仓（仅 3 仓有下载）、`acl` 20 仓（3 仓有下载）、`oauth` 58 仓、`policy` 43 仓（8 仓有下载）、`compliance` **8** 仓（1 仓有下载）。名称含 `audit` 104 仓但仅 15 仓有周下载。

### 1.2 已有的"单点"替代品为何不够

- `drscrewdriver/dsh-mcp-registry`（score 93.8、wk 2,521、+141.9%）是最接近注册中心的仓库，但标签仅 `[MCP,插件市场]`，**不含安全、不含工作流、不含路由**——只做登记，不做权限门控和审计。
- `lunnlew/dsh-oauth-mcp`（score 74.3、wk 1,203、+42.7%，标签 `[MCP,远程,安全]`）是唯一把 OAuth 与 MCP 结合的尝试，但体量小、age 仅 8 天，未成事实标准。
- `perrylink/dsh-mcp-panel`（score 95.2、wk 3,394）与 `appthin/dsh-mcp-manager-plus`（score 90.2、wk 1,163）是面板/管理类，仍缺"按角色授权 + 调用审计 + 配置治理"的完整闭环。

**企业场景缺口**：企业 IT 需要知道"公司里有哪些 MCP 工具、谁有权调用、每次调用留下了什么日志"。现有生态只回答了第一个问题的一小部分，后两个问题几乎无人回答。

## 2. 多模型路由与 Fallback

### 2.1 路由是"高需求 + 极低高质量供给"的典型

- 路由/网关(32) **1,191 仓，主榜 0 仓，`score≥90` 仅 9**（占 0.76%），周下载合计 171,911。
- 关键词侧：`router` 199 仓（`score≥90`=0）、`gateway` 84 仓（`score≥90`=0）、`proxy` 145 仓（`score≥90`=0）、`fallback` 37 仓（仅 1 个 `score≥90`）、`load-balance`/`loadbalancer` 均 **0** 仓——**企业级负载均衡/故障转移术语在生态里不存在**。
- 最讽刺的对照：`alice-marx/dsh-model-router` 周下载 4,686 却增长 **-70.1%**——典型"短命路由插件"，说明用户尝鲜后没有留存，缺的是可持续的治理能力而非一次性路由脚本。

### 2.2 矩阵格暴露的结构性空白

权威矩阵中，路由与"企业最关心的宿主"交叉极低：

- **工作区 × 路由 = 28**（new30=12，全矩阵最低区之一）
- **技能/Prompt × 路由 = 51**（new30=12）
- 会话管理 × 路由 = 83（new30=25）
- 智能体 × 路由 = 140
- 模型接入 × 路由 = 332（全矩阵最高，但这是"裸模型"层面，不是"工作区/技能"治理层）

全量标签统计亦印证：`路由∩成本`=147、`路由∩模型接入`=573，而 `路由∩工作区`=51、`路由∩技能`=77——路由插件扎堆在"模型层"，没有下沉到"项目/工作区/技能"这一企业真正要隔离的粒度。

### 2.3 仅有的 9 个高分路由仓库，没有一个是"企业网关"

`xdtrees/dsh-xdpool`（97.7，wk 4,734，+34.6%）、`dingminhua/dsh-connect-qoder`（95.6，wk 5,046）、`mrrisega/dsh-remote`（95.1）、`gychen-nju/dsh-game-daily`（94.2）、`hytime/dsh-thinking-effort`（93.2）、`drscrewdriver/dsh-union-search`（93.1）、`dddmuc/dsh-delete-session`（92.8）、`toby-bridges/api-relay-audit`（91.3，+143.9%）、`133563825as-ai/dsh-api-dashboard`（90.1）——多为**连接池、数字人/游戏、搜索、删除会话、审计面板**，没有"按项目配额隔离 + 自动 Fallback + 故障可观测"的完整网关。

Fallback 侧唯一亮点 `omdsh-dev/dsh-llm-fallbacks`（score 95.8、wk 3,572、+65.1%）标签仅 `[智能体,模型接入]`，**不含路由、不含成本、不含监控**——证明 Fallback 有需求，但没人把它做成可治理的链路。`helloqingtao/dsh-model-fallback-queue`（score 65.2、wk 380、+113.5%）增长强劲但量级太小。

**企业场景缺口**：多团队共用一个底座时，需要"每个项目独立路由策略 + 主备模型自动降级 + 降级事件告警"。现状是路由脚本遍地、治理网关为零。

## 3. 统一模型接入与密钥健康检测

### 3.1 "接入"很多，"健康检测"极少

- 模型接入(31) **5,420 仓**（周下载 964,553）是生态第二大标签，但 `score≥90` 38 仓。
- 密钥/健康相关关键词严重不足：`api-key` 仅 3 仓、`apikey` 仅 1 仓、`credential` 15 仓、`secret` 37 仓、`health` 45 仓、`key` 192 仓、`quota` 152 仓——大量 Provider 接入插件，几乎没有密钥生命周期管理。
- 关键交集：**模型接入 × 诊断/自检(46) 仅 22 仓**（主榜 0，`score≥90`=0，周下载合计 4,220）；模型接入×安全 326 仓、×统计/监控 353 仓、×成本 693 仓。也就是说，密钥过期、额度耗尽、Provider 故障这类"健康"问题没有诊断入口。

### 3.2 现有的"密钥"仓库都是单点修补

- `goodandready/dsh-key-rotation`（score 75.9、wk 1,927、增长 **-17.8%**）——唯一像密钥轮换的仓库，已衰退。
- `xrc111/dsh-apikeys`（score 72.5、wk 1,097、+35.3%，标签 `[Git,模型接入,安全,插件市场]`）——age 仅 9 天，未验证。
- `coh2357/dsh-workspace-api-key`（score 68.6、wk 2,141、-21.3%）与 `xiaozhe7772222/dsh-api-key-pool`（score 62.9、wk 0）——分别是工作区密钥与密钥池，均未成规模。
- `dingminhua/dsh-connect-workbuddy`（score 97.5、wk **34,342**、+12.3%，标签 `[模型接入,成本,插件市场,安装/管理]`）是下载榜第 18 名，证明"连接外部平台"需求真实且量大，但它不做密钥健康检测。

**企业场景缺口**：企业密钥分散在各 Provider 插件里，没有统一"健康看板"回答"哪个 key 快过期/哪个额度见底/哪个 Provider 在降级"。这是可审计治理的底层缺失。

## 4. 插件安装治理与更新

### 4.1 供给量大但"治理"维度缺失

- 安装/管理(41) **3,001 仓**，但**主榜仅 1 仓**、`score≥90` 仅 10（0.33%），周下载 507,178、增长中位 **-0.5%**。
- 关键词侧：`manager` 554 仓、`update` 132 仓、`upgrade` 28 仓、`install` 49 仓、`version` 18 仓，但 **`uninstall` 仅 1 仓**（`mayucong6/dsh-batch-uninstall`，wk 282）——"装得上、卸不掉、更不动"是典型企业痛点。
- 治理交集：`安装/管理×安全` **164 仓，增长中位 -5.8%**、`安装/管理×插件市场` 254 仓（增长中位 -4.5%）、`安装/管理×插件合集` 仅 45 仓——**安装治理是少数几个负增长的治理维度**。

### 4.2 更新/审批类替代品都是单点、低分

- `featherhunter/dsh-plugin-update`（score 72.3、wk 8,056、增长 -11%）——下载最高的更新插件，但已在衰退。
- `darkings/dsh-plugin-update-center`（score 76.6、wk 1,397）、`chendaleiq/dsh-plugin-auto-update`（score 68.9、wk 1,026）、`spheritier/dsh-plugin-bulk-update`（score 68.4、wk 776）——更新中心/自动/批量各做各的，无统一治理。
- `wqx11235/dsh-upgrade-guard`（score 64.6、wk 0）与 `oldzhang82/dsh-conservative-upgrade`（score 56.5、wk 0）——"升级守卫/保守升级"有理念但零下载。
- 唯一带治理味道的高分仓库 `noob-stupid/dsh-plugin-gating-hub`（score **92**、wk 6,969、标签 `[命令行,安全,插件市场,安装管理]`）证明"安装门禁"有市场，但没有形成标准。

**企业场景缺口**：企业需要"插件白名单/灰度发布/批量回滚/许可证与来源审计"。现状是 3,001 个安装脚本，缺一个"安装治理控制台"。

## 5. 远程/移动端安全接入

### 5.1 连接需求旺，安全是明显短板

- 远程/隧道(14) **1,024 仓**（周下载 363,371）、移动端(15) **687 仓**（周下载 251,867），需求真实：`flymysql/dsh-remote` wk 79,516（+76.8%）、`wnluo/dsh-mobile-plugin` wk 58,280（+60%）、`liguobao/ds-harness-remote` wk 30,117——远程/移动是任务一确认的高增长方向。
- 但安全交集极薄：

| 交集 | 仓库数 | 主榜 | `score≥90` | 周下载中位 |
|---|---|---|---|---|
| 远程 × 移动 | 208 | 0 | 10 | 638 |
| 远程 × 安全 | **77** | 0 | **0** | 205（远程整体 447 的 46%） |
| 移动 × 安全 | **32** | 0 | **0** | 474，仅 5 仓有下载 |

- 关键词侧：`tunnel` 仅 24 仓、`vpn` **7 仓且周下载合计为 0**、`ssh` 135 仓——加密隧道/VPN 类企业安全接入几乎空白。
- 唯一把三者结合的 `ebhrz/dsh-relay`（score 78、wk 4,515、+40.8%，标签 `[远程,移动,安全]`）age 仅 13 天，尚未成气候。
- 认证类尝试 `ai-eks/dsh-auth-tunnel`（score 67.4、wk 283）量级过小。

**企业场景缺口**：员工用手机/外网接入公司 Agent 时，企业要的是"设备合规校验 + 端到端加密 + 会话水印/审计"。现有远程插件解决"连得上"，没人解决"连得安全且可追溯"。

## 7. 横向证据：底座垄断与治理赤字互为因果

- **底座垄断**：框架/运行时(45) 1,795 仓，官方 `deepseek-ai/deepseek-harness` 周下载 1,208,788 = **90.4%**，第三方最高仅 4,105（`drscrewdriver/dsh-thinking-levels`）。这意味着所有企业治理需求都必须"寄生"在官方底座上，第三方无法自己造底座——**治理层是唯一可行的差异化空间**。
- **治理赤字**：安全(39) 1,848 仓，`score≥90` 仅 10（0.54%）、主榜 3 仓。高分安全仓库如 `drscrewdriver/dsh-session-guard`（94.9、+222.8%）、`perrylink/dsh-doublecheck`（95.6、+66.9%）、`mrweicodes/dsh-permgate`（91.5、+66.9%）、`hunmer/dsh-team-control`（93.5、+61.8%）、`bushizhanghan/dsh-publish-gate`（77.2、+71.9%）——增长都在 60%+，说明**治理类插件一旦做对就有强需求**，只是没人把它们整合成"统一纳管"产品。
